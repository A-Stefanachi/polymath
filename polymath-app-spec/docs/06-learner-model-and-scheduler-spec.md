## 1. Design principles and evidence limits

1. **Two separate models, on purpose.** (i) A *memory model* (FSRS, one card per skill) decides **when** a skill is next retrieved. (ii) An *ability model* (Elo/IRT-lite, one rating per skill) decides **how hard** the next item should be and how much to trust a result. Mastery and tier are **rule-based on logged attempts**, not on either model's output, so every state change can be explained in one sentence ("3 unaided correct answers on 3 different days and 3 different problems").
2. **FSRS evidence is about recall prediction, not learning outcomes.** FSRS-6 beat SM-2 on log loss for about 99.6% of users in a community benchmark of about 10k Anki users (about 350M reviews), and a neural model beat FSRS [V, `memory_practice_science.md` section 1]. No trial shows FSRS improves conceptual or procedural learning, and its parameters were fitted on flashcards. We therefore use it as a *default spacing engine with fresh problem variants*, an engineering inference [inf]. The evaluation plan (section 12) tests whether spaced, variant-based review predicts unaided checkpoint performance.
3. **Simple explainable ability model.** Deep knowledge tracing has similar AUC (~0.8) to simpler models but cold-start and order-sensitivity problems [V, `ai_adaptive_tutoring.md` section 1]. Elo/IRT-lite is what Duolingo's Birdbrain generalises and what production systems use [V]. We use it.
4. **Frontier ("outer fringe") selection** is plausible, but its public evidence is vendor-linked (ALEKS-style knowledge-space fringe, reported by its own authors) and there is no independent trial [B, Report A "Prerequisite-graph selection and mastery gating"]. We use it with hard prerequisites gating and soft prerequisites ordering as an engineering choice [inf], and the evaluation plan treats it as a hypothesis.
5. **Interleaving** helps mainly for confusable categories [V, `memory_practice_science.md` section 3]; that it should wait until "basic fluency" is an inference from cognitive-load reasoning, not a tested staging policy [inf, 02 M04]; the Grade-7 d=0.83 result is one large trial and is not a planning number (meta-analytic g about 0.34 for math is). Therefore: blocked first, within-module interleaving only after fluency, cross-discipline mixing only in capstone steps and checkpoints.
6. **No 90-minute rhythm.** Session lengths are user-chosen. The 20/90/180-minute defaults are scheduling conveniences, not physiology [no source supports ultradian learning cycles].
7. **Nothing here is a claim.** "Target success 0.80" is a tunable, not "the 85% rule".

## 3. Per-skill FSRS usage

### 3.1 Unit of scheduling

One FSRS card per `(user_id, skill_key)`, stored in `skill_state`. A review is **a skill, not an item**. Each review serves a **freshly generated item variant** (new seed; contract 7.3).

### 3.2 Which attempts create reviews

| Task kind | Creates FSRS review? | Updates Elo? | Counts toward mastery? |
|---|---|---|---|
| `worked_example` | no | no (weight 0) | no |
| `faded_problem` | no | yes, weight x0.5 | no (scaffolded) |
| `retrieval`, `problem`, `perceptual_drill`, `debug_case`, `explain_back` | yes | yes | yes if unaided and correct |
| `checkpoint` | yes | yes | yes |
| `diagnostic` | no (card created at the first verification review, see 3.6) | initialises (section 5.5) | counts as 1 qualifying attempt on the probed skill if unaided, correct, verified, constructed-response |
| `project_step` | no | no | no (accepted project evidence gives project credit, which satisfies only the "applied" condition, section 4.6; it is not an attempt) |

**First card creation:** the card is created at the **same-day `retrieval`** that ends the learning loop (contract 7.3), via `new_card(now)` then `review(card, rating, now)` when that retrieval's review unit commits (3.3). If the learner never reaches that retrieval, no card exists and the skill stays `learning` with `loop_step` set; the builder emits the retrieval next session as `retrieval_same_day` marked `late`.

### 3.3 One review per skill per session ("review unit")

All review-eligible attempts of one skill **within one session** are aggregated into one review (`aggregate_attempts` in the reference): `score` = mean, `max_hint_level` = max, latency ratio = lower median of `latency_ms/expected_ms`, `confidence` = lower median. Rationale: an interleaved set of 4 items on 2 skills must not give 4 independent reviews minutes apart (FSRS assumes spaced reviews; same-session repeats carry little new information) [inf].

Additionally **at most one `review_log` row per skill per local calendar day**. A second session the same day still updates Elo and mastery attempts but writes no `review_log` and does not call `review()`.

**When state is applied (00a H15).** Two writes happen at different times.

1. **Per attempt, at grading.** The state transaction runs `update attempts set state_applied_at = now() where id = $1 and state_applied_at is null`. If no row changes, the attempt was already applied and the transaction writes nothing. If a row changes, the same transaction applies Elo, `n_attempts`, mastery, tier and `loop_step`. Every graded attempt is stamped, including one with no learner effect (for example `worked_example` weight 0, or `grade.mastery_eligible = false`), so reconcile never returns to it. `review_log` is not an applied marker: most attempts in a unit have no row of their own.
2. **Per review unit, at session close.** FSRS `review()` and the `review_log` row run once per skill when the session closes: on `POST /sessions/{session_id}/complete`, with or without `abandon`, or at the idle timeout. The unit aggregates the skill's graded, stamped, review-eligible attempts in that session. `attempt_id` is the unit's last attempt, `attempt_ids` holds all of them, and `reviewed_at` is the last attempt's `submitted_at`, so a late close does not move the review to another day. `review_log_session_skill_unique` makes the commit idempotent.

**Idle timeout.** The server closes an `active` session as `abandoned` when `now` passes the last activity by `max(session_idle_timeout_min, planned_min)`, so a long bench gap in a lab session does not end it. Last activity is the latest of `started_at`, the attempts' `submitted_at` and the tasks' `completed_at`. `ended_at` is set to the last activity, and `session_ended` carries `ended_reason = idle_timeout`.

**Grades that are not ready at close.** A unit waits while an attempt of that skill in the session is `pending`, for at most `review_unit_grade_wait_min` after close; it then commits with what is graded. `pending_review` does not hold a unit, because a human may take days. A grade that arrives after its unit committed gets step 1 and never changes the committed unit. If no unit committed for that skill and session, the attempt forms a unit of one, subject to the local-day limit above.

**Attempts with no session.** With `session_id` null the attempt is its own unit, committed in the step 1 transaction.

**What the learner sees.** Until the unit commits, `skill_update.rating` in `AttemptResult` is null and `next_due` keeps the card's current value. `review_scheduled` fires at the commit.

Worked example (vector `agg-two-items`): two items, scores 1.0 and 0.0, hints 0 and 1, ratios 0.5 and 1.5, confidence 4 and 2 -> unit score 0.5, max hint 1, ratio 0.5, confidence 2.

### 3.4 Rating mapping (graded attempt/unit -> 1 Again, 2 Hard, 3 Good, 4 Easy)

Inputs: `score` s in [0,1]; `max_hint_level` h; `latency_ms` and `expected_ms` (ratio r = latency/expected, active time only: idle gaps over 45 s and tutor-panel time are subtracted client-side) and `template_n_obs` (number of graded observations of the item's template, supplied by the caller; **latency gate, 00a G5: while `template_n_obs < 20` (`latency_min_obs`) the ratio r is treated as missing, so rows 3 and 4 below cannot fire; a missing field counts as 0**); `confidence` c in 1-5 (asked **before** feedback; optional); the card's `reps`; grader type. Evaluated top to bottom, first match wins (function `map_rating`):

| # | Condition | Rating | Flags |
|---|---|---|---|
| 1 | `h = 4` (solution revealed) **or** `s < 0.5` | 1 Again | `high_confidence_error` if `c >= 4` and `h < 4` |
| 2 | `s < 0.8` **or** `h >= 2` | 2 Hard | |
| 3 | `r > 2.0` | 2 Hard | `slow` |
| 4 | `s >= 0.95` and `h = 0` and `r <= 0.6` and `c >= 4` and `reps >= 2` and grader is not `multiple_choice` | 4 Easy | |
| 5 | otherwise | 3 Good | `low_confidence_correct` if `c <= 2` |

Notes: (0) the latency gate is the only thing G5 changes in this table: score, hint and confidence rows apply from the first attempt; the caller still logs `latency_ms`, `expected_ms` and the ratio, and records `latency_rows_ignored` in the review flags it keeps itself, so the rows can be switched on retroactively for analysis. Consequence: Easy cannot be earned on a template with fewer than 20 observations (a lean slice with one template per skill reaches 20 observations only after many reviews, so for a long time most ratings are Again, Hard or Good), which keeps intervals shorter early; this is intended [P]. For an aggregated review unit (3.3) the weakest attempt decides: `aggregate_attempts` carries `template_n_obs` = the minimum over its attempts. (a) Level 1 hints (nudge) keep Good, consistent with the contract's "unaided = no hints above level 1". (b) Missing latency or confidence disables only the rules that need them (never Easy without both). (c) Easy is deliberately hard to earn: it lengthens intervals the most and a wrong Easy is costly. (d) A multiple-choice answer can never be Easy (guessing floor). (e) `high_confidence_error` also triggers a misconception note in the feedback screen and an extra-weighted Elo update (section 5.4) and queues one extra `retrieval` on the same skill in the next session (reason `hypercorrection_recheck`) [P: hypercorrection-style emphasis, `memory_practice_science.md` confidence section, [R]].

Vectors: `rate-good`, `rate-easy`, `rate-easy-first-rep`, `rate-easy-mc`, `rate-slow`, `rate-hint2`, `rate-hint1`, `rate-partial`, `rate-wrong-hiconf`, `rate-reveal`, `rate-faded` (these eleven now carry `template_n_obs = 25` so that they keep testing the rows they always tested), and the G5 vectors `rate-slow-ignored-n5`, `rate-slow-ignored-n19`, `rate-slow-n20`, `rate-easy-ignored-n5`, `rate-easy-no-obs-field`, `rate-hint-rows-unaffected-n0`.

**Worked examples (outputs of `map_rating`; added by the design review to remove ambiguity).** All have `grader_type = exact_numeric` unless stated; `r` is latency over expected latency.

| Attempt | Rating | Flags | Which row decides |
|---|---|---|---|
| score 1.0, no hint, r 0.5, confidence 5, reps 3 | 4 Easy | none | 4 |
| same, but `reps = 1` | 3 Good | none | 5 (Easy needs `reps >= 2`) |
| same, but `multiple_choice` | 3 Good | none | 5 (note d) |
| score 1.0, hint level 1, r 1.0 | 3 Good | none | 5 (level 1 keeps Good) |
| score 1.0, hint level 2 | 2 Hard | none | 2 |
| score 0.7 (partial credit), no hint | 2 Hard | none | 2 (partial credit is a success for FSRS but not a *correct* attempt for mastery, section 4.1) |
| score 0.45, confidence 5 | 1 Again | `high_confidence_error` | 1 |
| score 1.0, r 2.4 | 2 Hard | `slow` | 3 |
| score 1.0, confidence 5, reps 3, no latency recorded | 3 Good | none | 5 (never Easy without both latency and confidence, note b) |
| score 1.0, confidence 2, r 1.0 | 3 Good | `low_confidence_correct` | 5 |

Two properties worth knowing when reading the logs: (i) a partial-credit score between 0.5 and 0.8 lengthens the FSRS interval (Hard is a success) yet does not count as a qualifying attempt, so the memory model and the mastery rule can disagree by design; (ii) the latency rows (3 and 4) depend on `expected_ms`, which at the start is an authoring guess (`body.expected_s`); from contract v1.2 they are ignored until the template has 20 observations, so a slow novice is no longer mis-rated as Hard by a guessed expectation (`00f-design-review.md` F-09, decided as G5).

### 3.5 Target retention, lapses, fuzz, intervals

- `desired_retention` (contract 7.4, 00a G5; function `desired_retention(weeks_since_start, observed_minus_predicted)`): **0.85 for the learner's first 8 weeks** (`retention_initial_weeks`); from week 8 it is **0.90 only if the calibration monitor (3.8) reports observed minus predicted recall within 0.07** in absolute value (`retention_calibration_tolerance`, two-sided: a model that is far too pessimistic is also not trusted), otherwise it stays at 0.85; with no calibration data (fewer than 30 reviews beyond day 1) it stays at 0.85. Range 0.80-0.95 per user, experiment-variable. Why: the model of section 14 gives more mastered skills and fewer reviews due at 0.85 while the memory model is unvalidated for fresh variants [inf]; 0.90 is earned by evidence. Higher values increase review load; this trade-off is simulated by the FSRS community, not an RCT [R]. Vectors `retention-*` (seven).
- `maximum_interval_days` default **180**: the learner is weeks-to-months into a curriculum; capping keeps a check on long-interval skills and bounds damage from the unvalidated parameters.
- **Learning steps disabled** (`enable_short_term = false`): every task is a day-level event; the same-day retrieval is explicit in the loop. A lapse therefore produces a relearning card due **the next local day** (minimum interval 1 day).
- **Lapse** = rating 1. The library handles stability reduction and `lapses += 1`. Additionally the scheduler sets `mastery_state = decayed` if the skill was mastered (section 4.3).
- **Fuzz:** enabled. Production passes a seeded RNG: `seed = fnv1a(user_id + "|" + skill_key + "|" + reps)` so reviews are reproducible in tests and replay. If the library cannot take a seed, wrap fuzz off and apply the same fuzz ourselves: for intervals >= 3 days, `interval * (1 + u)` with `u` deterministic uniform in [-0.05, +0.05] from the seed, rounded to whole days, never below 1 day.
- **Due comparison is day-granular:** a skill is *due* when `due <= end of today in the learner's timezone`. This batches reviews into the day's micro session and avoids "due in 3 hours" noise.
- **Elapsed days and long absences:** FSRS uses real elapsed days; a skill reviewed after 40 days with a Good rating is handled by the library. We never rescale `due` after an absence (section 10.2).

### 3.6 Diagnostic and inferred skills

A correct diagnostic answer creates provisional **placement credit** only (00a B6). The probed skill is written `reviewing` with `skill_state.source = placement`; inferred ancestors are written `learning` with `diag_credit = true`. Neither has an FSRS card: the card is created at the first verification retrieval (rating mapped as usual). A placement card in `reviewing` satisfies the frontier test for 14 days regardless of retrievability (section 6.1) until its first verification review. A failed verification review sets the skill to `learning` and removes the placement credit. Diagnostics never set `mastered` (section 5.5); the 4.3 definition of `reviewing` (2 qualifying attempts on 2 days) is waived for placement cards, which is why `source` is stored.

### 3.8 Fresh item variants per review

FSRS was fitted on identical cards. A fresh variant tests *transfer to new numbers*, a stricter event than re-recalling the same card, so predicted retrievability may be optimistic [inf]. Controls:

1. **Difficulty match:** pick the template whose `difficulty_est` is nearest `d* = theta - 400*log10(0.8/0.2) = theta - 240.8` (function `target_item_difficulty`; theta 1500 -> 1259.18). Ties: template least recently used for this skill. Restrict to templates with `tier >= skill.tier_target` while the skill is below mastered (so reviews also count toward mastery). **Worked consequence (design review F-14):** priors span 1200-1800 (5.1), so `d*` is below every prior while `theta < 1440.8` (`d* = 1200` at that value). Starting at `theta = 1300` the rule therefore selects the *easiest* template of the skill until the learner's rating has risen about 140 points, and when a skill has one template (the lean-slice plan has 30 to 40 templates for 142 skills) the difficulty match does nothing at all. Qualifying attempts are therefore at the easiest in-tier difficulty early on; see the mastery discussion in `00f-design-review.md` F-03.
2. **No repeats:** never reuse a `seed`; never serve an item whose canonical answer string equals any of the last 5 answers served for that skill; avoid the template used in the last 2 reviews of that skill if another qualifies.
3. **Verified only** (contract 7.8).
4. **Calibration monitor:** log predicted retrievability `R_pred` (from the library, at review time, before the answer) on every review. Nightly job computes, for the last 300 reviews, Brier score and a 10-bin calibration table `(mean R_pred, observed share of ratings >= 2)`. Alert (log event `fsrs_miscalibrated`) if the absolute gap in the lowest-R bin exceeds 0.15. Parameter optimisation with the library's optimiser is allowed only after >= 1000 reviews [R: community guidance of roughly 1000 reviews; unverified] and behind the experiment flag `fsrs_params`.
5. **What else to watch (design review, 00f F-04).** The monitor above is global; the risk is specific. Also log, per review, the interval bucket (1-2, 3-7, 8-30, over 30 days), whether the template was the same as in the previous review, and the rating, and compare observed recall by bucket with `r_pred`. Two signatures matter: (a) observed recall below `r_pred` in the 8-30 day bucket means fresh variants are harder than FSRS assumes and intervals are too long (raise `desired_retention` or cap `maximum_interval_days` at 60); (b) a share of Hard and Again ratings that does not fall as reps grow means stability is not accumulating for this learner or skill type (procedural skills such as code and SPICE are the likely cases). The simulation of section 14.3 shows the cost of (a): reviews rise from about 106 to 140-190 minutes a week [inf].

## 4. Mastery, decay and tier attainment (canonical)

### 4.1 Definitions

- **Attempt**: a row in `attempts` with a verified grade. The scheduler ignores any attempt whose `grade.status` is not `graded` (`invalid_input`, `pending_review`, `error`; 00a B4), and any attempt whose `grade.mastery_eligible` is false (uncalibrated `rubric_llm`); such attempts are neither qualifying nor review-creating, although a learner still sees their feedback. **Review-eligible kinds**: `retrieval`, `problem`, `perceptual_drill`, `debug_case`, `explain_back`, `checkpoint`; `diagnostic` also qualifies as described in 3.2.
- **Unaided attempt**: `max_hint_level <= 1` and the solution was not revealed (level 4) (00a B1). `attempts.unaided` must equal this. The stricter evaluation term **strict-unaided** (`max_hint_level = 0` and no tutor panel opened) is derived in the view `v_attempts_strict_unaided` and is used only by document 11; the scheduler never reads it. In a `checkpoint`, any hint or tutor message voids the attempt (`unaided = false`); checkpoints expose no hint UI.
- **Correct attempt**: `score >= 0.8` (`correct_threshold`).
- **Qualifying attempt for tier T**: review-eligible kind, `unaided`, correct, from a **verified** item, and the item's `tier >= T`.
- **Local day**: calendar date of `submitted_at` in `profiles.timezone`.
- **Distinct variant**: distinct `items.id` (every item has a unique seed, so this is also distinct seeds).
- **Skill tier target** `T*` = `skills.tier_target`.

### 4.2 The mastery rule

A skill is **mastered** when, counting only attempts since `epoch_start` (4.4), **all** of the following hold at tier `T*`:

1. at least **3** qualifying attempts;
2. on at least **2** distinct local days, **and the first and last qualifying attempts are at least `mastery_min_span_days` = 2 learner-local calendar days apart** (00a G3; calendar-date difference in `profiles.timezone`, so the minimum elapsed time is just over 24 hours);
3. on at least **2** distinct item variants (distinct `items.id`), **drawn from at least `mastery_min_templates` = 2 distinct verified templates when the skill has 2 or more verified templates** (00a G3; the caller passes `n_verified_templates` and each attempt carries `template_key`; with one verified template the condition is waived, and an attempt without a `template_key` cannot show diversity);
4. the **last two graded unaided review-eligible attempts** both have `score >= 0.5` (a fresh failure blocks mastery until recovered);
5. **constructed-response**: at least one qualifying attempt has `grader_type != multiple_choice`, unless the skill has no verified non-MC template;
6. **applied** (only when `T* >= L1`): at least one qualifying attempt is `problem`, `debug_case` or `checkpoint`, unless the skill has no verified template of those kinds.

Conditions 1-6 with the two G3 clauses are the canonical rule (00a B3, G3; contract 7.5). The reference keeps the output shape of `mastery_rule` unchanged: the span clause is folded into the `days` check and the template clause into the `variants` check (`checks` still has the six keys), so the TypeScript port reports the same six booleans. **Project credit (00a B5):** an *applied* project credit (section 4.6) satisfies condition 6 only; it is not an attempt and counts toward conditions 1-5 not at all (vectors `mast-project-credit`, `mast-no-project-credit`, `mast-project-credit-only`). Function: `mastery_rule`, vectors `mast-*`. Examples:

- Attempts: day 24 `problem` i1 correct, day 25 `retrieval` i2 correct, day 27 `problem` i3 correct, all unaided, tier L1 -> met (3 qualifying, 3 days, 3 variants).
- Three correct attempts on one day -> `days` check fails (`mast-one-day`). Same item thrice -> `variants` fails. A hint-level-2 attempt among them -> only 2 qualify (`mast-hint2`). Three MC-only correct answers -> constructed-response fails (`mast-mc-only`); allowed if the skill has no non-MC template (`mast-mc-only-no-alt`). Items below the skill's tier do not qualify (`mast-l0-items-for-l1`).
- Timezone: attempts at 23:30Z on 24th, 00:10Z and 09:00Z on 25th are 2 local days in UTC, 1 day at UTC+2 (`mast-day-boundary-tz`, which passes `mastery_min_span_days = 0` since v1.2 so that it keeps testing the day boundary alone, and `-tz2`).
- Span (G3): days 24, 25, 27 pass (`mast-met`, span 3); days 24, 25, 26 pass exactly (`mast-span-exactly-2`); days 24 and 25 only fail even when the attempts are 20 minutes apart across midnight (`mast-span-default-blocks`) or a day apart (`mast-span-1-day-short`); the span is counted in local days (`mast-span-local-days`); `mastery_min_span_days = 0` restores the v1.1 behaviour (`mast-span-gaming`).
- Templates (G3): two verified templates but all three attempts on one template fails the variants check (`mast-tpl-single-blocks`); two templates pass (`mast-tpl-two-ok`); a skill with one verified template is unaffected (`mast-tpl-only-one-exists`); missing keys fail (`mast-tpl-missing-key`); `mastery_min_templates = 0` switches the clause off (`mast-tpl-param-off`); `state-reviewing-single-template` shows the skill staying `reviewing`.

**When can a new skill first be `mastered`? (timeline under the v1.2 rule, standard loop, all attempts correct and unaided).** Day 0: worked example, faded problem and the same-day `retrieval` (qualifying attempt 1; it comes minutes after the worked example, so it measures very little forgetting). Day 1: the `practice` problem (attempt 2, applied; the skill becomes `reviewing`). Day 2 at the earliest, in practice day 3 or so: the first FSRS review, whose first interval is about 3 days after a Good first rating [inf from FSRS-6 defaults, recalled; the pinned library decides] (attempt 3: count 3, days 3, span 2 or 3 calendar days, variants 3, constructed-response, applied: **mastered**). So the earliest mastery is still about 3 days after first exposure, and a skill is `mastered` before any retrieval has been tried after a week. That is deliberately cheap (it keeps the frontier moving), but it means `mastered` is a statement about three short-term successes, not about durable retention; the decay rule (4.3) and the unaided checkpoints (section 8) are what catch the difference. The two loopholes found by the design review are closed by G3: attempts at 23:50 and 00:10 no longer count as a span (the first and last qualifying attempts must be two calendar days apart), and a single easy template can no longer supply every qualifying attempt when two verified templates exist. The same-day retrieval still counts as an attempt. Cost in the model of section 14: about 8 fewer skills `mastered` at week 12 (span 2 against span 0), and the first project skills arrive a few weeks later [inf]; the cheaper remedy for the wait is a guided first build with L0 credit (00a B5), not a weaker rule.

### 4.3 State machine (`mastery_state`)

| State | Definition (function `mastery_state`) |
|---|---|
| `unseen` | no attempts on the skill |
| `learning` | has attempts; neither `reviewing` nor `mastered` |
| `reviewing` | at least 2 qualifying attempts on at least 2 distinct local days, rule not yet fully met |
| `mastered` | rule 4.2 met, not decayed |
| `decayed` | was `mastered` (`ever_mastered`) and (current retrievability `< 0.70` **or** last rating was 1) |

Transitions:

- `learning/reviewing -> mastered` the moment the rule is met after an attempt is written (also requires current R >= 0.70 and last rating != 1).
- `mastered -> decayed` evaluated (a) after every attempt and (b) by a nightly job over all mastered skills using the library's retrievability. `decayed` does **not** erase `tier_attained`.
- `decayed -> mastered`: **one** qualifying attempt on a fresh variant made after the decay moment, or **two qualifying attempts on two different days** if the skill had 2 or more lapses in the last 60 days (`recent_lapses_60d`). Vectors `state-remastered`, `state-remastered-2lapse`.
- **`needs_applied` (00a G2; derived at read time, no column).** A `reviewing` skill is flagged when the only unmet condition of the rule in 4.2 is condition 6 (function `needs_applied`; vectors `needs-applied-yes`, `-count-also-short`, `-span-also-short`, `-mastered`, `-project-credit`, `-l0-skill`, `-no-applied-template`). The packer treats a flagged skill as in progress (7.4 step 2b). It is not a state: the five `mastery_state` values are unchanged.
- A decayed skill is treated as *due now* by the builder (reason `due_review`, flagged `relearn`); if the relearning retrieval scores < 0.5, its `loop_step` resets to `worked_example` after a second consecutive failure (a worked example is re-shown before another attempt).
- Dependents of a decayed prerequisite stop being *available* (section 6), except in-progress skills with prerequisite R >= 0.70 (hysteresis).

### 4.4 Mastery epoch

`epoch_start` is set when the skill is first attempted and reset (a) by a trace-back demotion that restarts the skill (10.3) and (b) never by ordinary decay. Attempts before `epoch_start` stay in the log but do not count. `ever_mastered` resets to false when `epoch_start` resets.

### 4.5 Why these numbers

3 successes over 2 days with different variants operationalises "successive relearning" lite [R, `memory_practice_science.md` section 2: correct retrieval in each of N sessions]; it is a **[P]** threshold, not an evidence-derived cut-off. The evaluation plan tests it: unaided checkpoint accuracy on `mastered` skills vs `reviewing` skills (section 12); if mastered skills fail checkpoints more than 30% of the time at 14+ days, raise `mastery_min_correct` or the day count by an experiment.

### 4.6 Tier attainment (`skill_state.tier_attained`, nullable)

Evaluated whenever the skill's mastery rule is re-evaluated; tiers are cumulative and never skipped (function `tier_attained`):

| Tier | Rule |
|---|---|
| `L0` | mastery rule (4.2, conditions 1-5; condition 6 not required) satisfied counting qualifying attempts on items of any tier |
| `L1` | full mastery rule with `T = L1` (items with `tier >= L1`, condition 6 required) |
| `L2` | full mastery rule with `T = L2` **and** at least one qualifying `checkpoint` attempt at tier L2 **and** the span between first and last qualifying attempt is at least 14 days |
| `L3` | never automatic; set only by a `human_review` outside the MVP plus L2 on the skill. **No project grants L2 or L3** (00a B5) |

**Project credit (00a B5).** Completing a verified project step writes rows to `project_grants`: L0 credit is applied immediately; L1+ credit is **pending** and becomes real (`applied`) only when the step's `project_evidence` reaches `accepted`. Applied credit satisfies only the "applied" condition (6) of the rule at tier L1 and the module-level L1 condition below; function inputs `project_credit_applied` of `mastery_rule` and `tier_attained` (vector `tier-project-no-l2`). Pending credit changes nothing in the scheduler, except that document 10 asks for a checkpoint priority bump on skills with pending or assisted credit (a content-ordering hint only, not a rule).

`tier_attained` only ever increases automatically. If a skill's `tier_target` is below the tier a dependent edge requires, the edge cannot be satisfied and content validation must flag it (`validate_graph`).

**Node/learner-level tiers** (progress screen only, derived, not stored): a node is "L1 working" when >= 90% of its skills with `tier_target <= L1` have `tier_attained >= L1` **and** the node's L1 gate project (`projects.tier_gate = L1`) has all required `project_evidence` at `accepted`. Anything less is shown as a count ("14 of 17 skills at working level"), never as a single badge. Hour ranges in the research report are [P] and not shown as promises.

Vectors: `tier-l1`, `tier-l2-needs-checkpoint`, `tier-l2`.

## 5. Elo / IRT-lite ability model

### 5.1 Quantities

- `skill_state.elo` = ability theta for that skill, Elo scale (400 points = 10:1 odds).
- Item difficulty `d` lives on the **template** (`item_templates.difficulty_est`, with `n_obs`); variants of a template inherit it (`items.difficulty_est` is copied at render time). Variants differ only in numbers, so pooling their evidence is correct; authors must keep variants within one difficulty band, and a template with `|calibrated d - prior d| > 300` after 30 observations raises `needs_human_review`.
- Prior: `d0 = 1200 + 600 * difficulty_prior` (so priors span 1200-1800). Function `difficulty_from_prior`.

### 5.2 Expected score

`E = g + (1 - g) / (1 + 10^((d - theta)/400))`, where `g` is the guessing floor: `1/n_options` for `multiple_choice` (from `body.mc_options`), 0 for every other grader. Examples: theta 1500, d 1500 -> 0.5; d 1900 -> 0.0909; MC with g = 0.25 at equal ratings -> 0.625.

E is a model score, **not** a calibrated probability; it is used for item selection, fading decisions and diagnostics only. Calibration is logged (section 12).

### 5.3 K-factor schedule

`K(n) = max(16, 48 / (1 + n/10))` where n = `skill_state.n_attempts` for the learner side. Values: K(0)=48, K(10)=24, K(>=20)=16. Item side: `K_item(n) = max(4, 24 / (1 + n/20))` with n = template `n_obs`. [P]

### 5.4 Update rule and weights (function `update_elo`)

For one graded attempt with score s (forced to 0 when `max_hint_level = 4`):

```
E       = expected_score(theta, d, g)
w       = learner_weight(attempt)                      # table below, in [0, 1.25]
theta'  = theta + K(n_skill) * w * (s - E)
d'      = d - K_item(n_item) * (s - E)   if item_informative else d
n_skill += 1 if w > 0 ;  n_item += 1 if item_informative
```

| Situation | Learner weight w | Item update |
|---|---|---|
| unaided (max hint <= 1), normal | 1.0 | yes |
| hint level 2 (conceptual hint) | 0.5 | no |
| hint level 3 (worked step) | 0.25 | no |
| hint level 4 (reveal) | score forced 0, w = 0.5 | no |
| `faded_problem` | x0.5 on top of the hint weight | no |
| `worked_example` | 0 (no update at all) | no |
| rapid guess: wrong, `latency < 3 s` and `< 0.15 x expected` | x0.5 | no |
| high-confidence error: `c >= 4`, `s < 0.5`, hint <= 1, not a rapid guess | x1.25 | yes |

"Item informative" = unaided, not scaffolded, not a rapid guess. Rationale: aided attempts tell us little about item difficulty, and learning during the attempt biases it.

Worked numbers (reference output):

- New skill, theta 1300, n=0, template d 1500, n_obs 0, unaided correct: E = 0.2403, K = 48, theta' = 1300 + 48 x 0.7597 = **1336.47**; item K = 24, d' = 1500 - 24 x 0.7597 = **1481.77** (vector `elo-correct-unaided`).
- theta 1500, d 1500, n=10, unaided wrong: E = 0.5, K = 24, theta' = 1500 - 12 = **1488.0**; item (n_obs 20, K_item 12) d' = **1506.0** (`elo-wrong-unaided`).
- Hint level 3, correct, theta 1400, d 1450: E = 0.4285, w = 0.25, K(5) = 32 -> theta' **1404.57**, d unchanged (`elo-hint3`).
- Reveal: score forced to 0, w = 0.5 -> theta **1393.14** (`elo-reveal`).
- High-confidence wrong, theta 1500: weight 1.25 -> theta' **1485.0** vs 1488.0 unweighted-at-confidence (`elo-hiconf-wrong`).

### 5.5 Cold start and diagnostic initialisation

- No information: `theta = 1300` (`elo_init_default`), `n_attempts = 0` (so K = 48).
- With prerequisites having ratings: `theta = clamp(mean(prereq theta) - 50, 1100, 1700)` (function `cold_start_theta`; e.g. [1500, 1600] -> 1500).
- **Diagnostic item result** with item difficulty d and unaided score s: `theta = d + 400*log10(p/(1-p))` with `p = clamp(s, 0.1, 0.9)`. So a correct answer on d=1500 gives 1881.70, a wrong one 1118.30, a half-credit 1500.0 (function `diagnostic_init`). Set `n_attempts = 3` so K starts at about 37 and later practice corrects it quickly.
- **Diagnostic procedure (00a G7; identical in 05 section 11.2).** `task_kind = diagnostic`; **constructed-response items only** (no multiple choice; the content validator rejects a diagnostic template whose grader is `multiple_choice`); **about 2.5 minutes an item** (`TASK_MINUTES.diagnostic`); **at most 20 items in at most two sittings of 25 minutes each**. A sitting is one `focus` session (00a A2) that ends at 25 minutes of active time or after 10 items, whichever comes first; the learner may stop earlier. The second sitting is offered from the next local day and resumes the stored set of unresolved skills (nothing is re-asked); results of sitting 1 are written immediately and already open dependents. There is a visible "I don't know" button (score 0 with weight 0 for Elo, counts as a probed-unknown answer). No extra table is needed between sittings: probed and inferred skills are already in `skill_state`, and the unresolved ones are exactly the skills with no row.

```
unresolved = all skills in scope (hard-edge DAG)
while items_done < 20 and unresolved:      # 10 per sitting, 25 minutes per sitting
    s = argmax over unresolved of  min(|ancestors(s) ∩ unresolved|, |descendants(s) ∩ unresolved|)
        tie-break: smaller depth, then skill key ascending
    serve one item of s at the template whose d is nearest the skill's median template d
    if correct (score >= 0.8, hint 0):
        s -> probed_known;  every ancestor via hard edges in unresolved -> inferred_known
    else:
        s -> probed_unknown;  every descendant via hard edges in unresolved -> inferred_unknown
```

  Results: `probed_known`: `mastery_state = reviewing` with `source = placement` (00a B6), theta from the formula, the diagnostic attempt counts as 1 qualifying attempt, `loop_step = verify`. `inferred_known`: `learning`, `diag_credit = true`, `loop_step = verify`, `theta = theta(descendant) - 100`, `n_attempts = 3`, no worked example or faded problem (expertise reversal: guidance helps novices and becomes redundant for the competent [R, `memory_practice_science.md` section 4]). `probed_unknown` / `inferred_unknown`: `unseen`, with theta from cold start. **No diagnostic result sets `mastered`**; inferred skills need the normal rule (3 qualifying attempts over 2 days) delivered as cheap `retrieval` verifications (builder reason `verify_inferred`, maximum 4 per session, no new-skill slot consumed). Dependents of a probed placement skill open under the 14-day grace of 6.1; dependents of an inferred skill open once it reaches `reviewing` with R >= 0.8 (normally 2 days). Verification retrievals are ranked together with due reviews (priority class (a), section 7.4). A skipped diagnostic means every skill starts `unseen` and the frontier is the graph roots (section 10.1). With 20 items about 16 skills of 142 stay unresolved for a novice and about 28 to 39 for a learner with background (section 14.5); unresolved skills are treated as `unseen`, and the "I already know this" skip (5.6) covers the rest.
- **Honesty:** a diagnostic with 20 items cannot establish what a learner knows; UI says "starting point estimate" and the first two weeks of verification overrule it (see `09-ux-and-flows.md`).

### 5.6 Where Elo is used

1. Item selection (`d*`, 3.8). 2. Skip/fade: if a new skill's cold-start `E >= 0.85` on its median template, offer "I already know this" which converts the skill to `verify` (three retrievals) rather than worked example. 3. Trace-back probe ordering (lowest theta first). 4. Readiness display ("likely to find this hard / comfortable"), never as a probability to the learner. **Not used** for mastery, tier or frontier availability.

## 6. Frontier computation

Inputs: skill graph (`skill_edges`), `skill_state` per skill, and a project-pull map. Reference: `compute_available`, `compute_frontier`, `frontier_scores`, `project_pull`.

### 6.1 Prerequisite satisfaction (contract 7.1, made precise)

For a hard edge `p -> s` with `min_tier` m (null = no tier requirement beyond mastery), the edge is **satisfied** when:

```
state(p) == mastered
   OR (state(p) == reviewing AND retrievability(p) >= 0.80)
AND  (m is null OR tier_attained(p) >= m)
```

`mastered` satisfies regardless of current R (it decays to `decayed` below 0.70). For a skill already `learning` (in progress) the retrievability threshold for `reviewing` prerequisites drops to **0.70** (hysteresis, `continue_r_threshold`) so a skill does not vanish mid-learning. `tier_attained = null` fails any non-null `min_tier`. **Placement grace (00a B6, G1).** A skill in `reviewing` with `source = placement` that has had no verification review and no failed `verify` retrieval is in its grace for `placement_grace_days = 14` days after placement. During the grace it satisfies the edge **regardless of its retrievability, and its tier counts as L1 for the `min_tier` test** (`placement_grace_max_tier = L1`): it satisfies `min_tier` null, L0 and L1, not L2. The relaxation is for this test only. The card is never `mastered`; `tier_attained` stays at most L0, which is what the progress screen, project credit and every other consumer read; and `prereq_satisfied` does not write anything. The grace ends early if a `verify` retrieval fails (the skill returns to `learning`, 3.6; the reference models this with the state flag `placement_verify_failed`), and normally at the first successful verification review (`verified_after_placement`), when the ordinary tests take over: by then the skill has real attempts, and an L1 edge needs `tier_attained = L1` as for any learned skill. After day 14 without verification the ordinary tests apply again. An inferred skill still in `learning` satisfies no edge (`prereq-placement-learning-state`). Vectors: `frontier-placement-grace`, `frontier-placement-expired`, `frontier-placement-verified` (v1.1, tier L1 states), and for G1 `frontier-placement-l0-grace`, `-grace-day14`, `-expired`, `-verify-failed`, `-verified`, `frontier-learned-l0-blocked` and the direct tests `prereq-placement-edge-l1`, `-edge-l2`, `-edge-null`, `-high-r-l1`, `-learning-state`, `-mastered-needs-tier`.

**Why G1 (found by the design review, 00f F-02, F-05).** In the shipped graph **227 of 239 hard edges carry `min_tier: L1`** and 12 carry L0 (counted from the YAML [inf: computed, not a source]). Without the relaxation a placed skill has `tier_attained` at most L0 (05 section 11.3) and would open no dependents across an L1 edge, so a diagnostic would remove teaching but not gating, contradicting the intent of 00a B6. With it, placement opens dependents for 14 days, long enough for the cheap `verify` retrievals (priority class (a), 7.4) to confirm or revoke the credit. For ordinary learned skills the branch "`reviewing` with R at least 0.8" is still inert across L1 edges (`tier_attained = L1` already implies the full rule, i.e. `mastered`), so in effect almost every dependent opens only after its prerequisite is `mastered`; that strictness is intended.

Further vectors: `frontier-min-tier` (divider at L0 does not open `elec.rc.rc-time-constant`, requiring L1), `frontier-min-tier-ok`, `frontier-decayed-prereq`, `frontier-mixed`.

### 6.2 Available and outer fringe

- **Available(s)** = every `hard` prerequisite edge into s is satisfied (skills with no hard prerequisites are always available).
- **Frontier (outer fringe)** = available skills whose `mastery_state` is `unseen` or `learning`. (`reviewing`/`mastered`/`decayed` skills are handled by the review path; `decayed` is not "new".)
- `hard` edges gate. `soft` edges **never** gate, only order (6.3).

### 6.3 Ordering the frontier

```
score(s) =  3.0 * pull(s)                       # projects need it (6.4)
          + 1.0 * unlocks(s)                    # share of direct hard dependents that would become available, capped at 3 / 3
          - 2.0 * unmet_soft(s)                 # fraction of soft prerequisites not mastered/reviewing
          - 2.0 * max(0, node_share(s) - 0.60)  # load balance (7.7)
          - 0.25 * est_minutes(s) / 60          # prefer cheaper skills, weakly
sort: (unmet_soft > 0.5) last, then score descending, then skill key ascending
```

So a skill whose soft prerequisites are mostly unmet is considered only when nothing better exists, which is how soft prerequisites order skills without gating them. Vector `frontier-scores` (project pull for the ADC step; elec already holding 75% of recent minutes): `sw.c.control-flow` 1.0832, `math.alg.exponents-logs` 0.0833, `elec.dc.kirchhoff-laws` -0.6125.

### 6.4 Project pull

`pull(s) = max over upcoming project steps (next 3 steps of the active user_project) of 1/(1+distance(s, step skill))` over hard **and** soft ancestors, distance = edges to the step's skill (`project_pull`; ancestors of the ADC step: voltage divider 0.5, gpio 0.5, ohms law 0.33...). No active project -> pull 0.

## 7. Session builder

Pure function `buildSession(input) -> {tasks[], total_est_min, fill, fits}`; reference `pack_session`. Contract 7.6: it returns an ordered task list whose estimated total fits the time; micro uses only phone-suitable tasks.

### 7.1 Inputs

`available_minutes`, `context` (`phone|desktop|bench`), `session_type`, learner `skill_state` snapshot (state, retrievability, `due` flag = due by end of local today, `loop_step`, `blocked_by`), the graph, interleave stages per module, `checkpoint` status (`none|due|overdue` and skill list), active project steps (lab), `project_pull`, node minutes over the last 7 days, `backlog` flags, experiment parameter overrides, `now`.

**Window rule (00a A1).** `session_type` is only `micro` (available minutes capped at 20), `focus` (45-120) or `lab` (120-240). There is no type for a 21-44 minute window: the caller serves it as one `micro` session and, when that session ends with time left, offers a second `micro` session (a separate `sessions` row, built by a fresh call with the remaining minutes). The builder never returns a session longer than its type allows, and project steps are never authored with `est_min` in 21-44. A diagnostic is built as one `focus` session whose tasks are `diagnostic` (00a A2).

### 7.2 Time estimation (minutes) per task kind

| Task kind | Default | Notes |
|---|---|---|
| `retrieval` | 1.5 | one short fresh item |
| `worked_example` | 4.0 | includes the self-explanation prompt and, on a skill's first example, the concept primer (00a K1, K11; unchanged value, corrected by the orientation ratio) |
| `faded_problem` | 5.0 | |
| `problem` | 10.0 | standard; `problem_short` = 4.0 for items with `body.short` (used in interleaved sets and phone) |
| `perceptual_drill` | 2.0 | |
| `explain_back` | 4.0 | |
| `debug_case` | 12.0 | |
| `diagnostic` | 2.5 per item (constructed response, 00a G7) | |
| `checkpoint` | 2.5 per item | |
| `project_step` | `project_steps.est_min` | |

**Reconciliation with the graph's `est_minutes` (00a G8; design review F-07).** The review compared two different quantities: 28 minutes a skill in the graph, and 10.5 minutes for the first chunk of a new skill in the builder. They are not rivals. `est_minutes` is the learner time from first exposure to first mastery; the builder spreads that time over several tasks. On the builder's own defaults a skill costs: first chunk 10.5 minutes in a micro session (worked example 4.0, one faded problem 5.0, same-day retrieval 1.5) or 15.5 in a focus session (two faded problems), one practice `problem` 10.0, and two retrievals for the second and third qualifying attempts 3.0: **28.5 minutes in a focus session, 23.5 in a micro-session chain** (add 10.0 for each extra problem a harder skill needs). The graph's mean of 28.6 minutes (graph 0.2.0) therefore matches the focus-session path, and the five slowest skills were re-timed upwards so that a skill needing three problems is not shown as two (05 section 6.2). Both figures stay author estimates [P] until the orientation sessions give actual/estimate ratios; the personalisation multiplier below is capped at 1.8 and should be raised to 3.0 if the measured ratio is above 1.8 (00f F-07). **Planning rate:** 5 to 7 new skills a week, never 20 (G8): 7 x 28.5 = 200 minutes of first learning against about 252 usable non-lab minutes leaves room for reviews only because the lab slot is served as a focus session when no project step is eligible (7.4, 7.8); at 5 a week the reviews of earlier weeks also fit. Section 14.1 gives the demand arithmetic.

**Personalisation:** after >= 5 completed tasks of a kind, `est = default x clamp(median(actual/default over the last 20), 0.6, 1.8)`. Template `body.expected_s` seeds the latency expectation `expected_ms` used by rating; the same multiplier scales it.

### 7.3 Phone-suitable filter

A task is phone-suitable when its kind is in `{retrieval, worked_example, faded_problem, perceptual_drill, problem_short, checkpoint}` **and** the skill's chosen template has `body.phone_ok = true` (numeric keypad, MC, tap or short text answers; no code editor, no schematic editing, no SPICE input). Excluded on phone: `problem` (standard), `explain_back` unless `phone_ok`, `debug_case`, `project_step`. `bench` context: no cards in `micro` (returns empty; the UI offers lab/focus or "log a bench note"); `project_step` only. `desktop`: all except steps flagged `bench_only`.

### 7.4 Packing algorithm

Budget `B = available x (1 - 0.10)`; for `micro`, available is first capped at 20. Packing is greedy by the contract 7.2 priority classes, then reordered for presentation. All ties break by skill key ascending (determinism).

```
0. If checkpoint == overdue: reserve and add checkpoint tasks FIRST (contract 7.2 (e), see CCR-3).
1. (a) Due reviews, lowest retrievability first, until review minutes reach 0.70 x B
        (1.00 x B when backlog flag set). Decayed skills are included as relearn reviews.
        Bundle: for a module with interleave stage >= 1 and >= 2 due skills, emit ONE interleaved set
        (width per 7.6, 2 items per skill, minimum 4, kind problem_short, strategy_prompt = true)
        instead of separate retrievals, if it fits and every item is phone-suitable on phone.
2. (b) Continuation of in-progress skills (state learning, loop_step set), at most max_new_skills[type]
        in total with (c): micro 1, focus 3, lab 0. Per loop_step:
          worked_example -> worked_example + faded_problem (+1 extra faded_problem in focus for new skills)
          faded_problem  -> faded_problem
          practice       -> one problem (problem_short on phone)
          verify         -> one retrieval (reason verify_inferred; max 4 per session; no slot used)
        A chunk is added only if it AND its same-day retrieval (1.5 min) fit; otherwise skip the chunk.
2b. (b2) Applied gap (design review F-01): each `reviewing` skill whose flag `needs_applied` is true (derived at read time from `mastery_rule(...).checks`, 4.3; the caller puts it in the state snapshot; its only open mastery condition is condition 6, *applied*; contract 7.2 (b), 00a G2) is *in progress* for the purposes of contract 7.2 (b): add one `problem` (`problem_short` on phone), at most `applied_gap_max[type]` per session (micro 1, focus 3, lab 0), ranked by number of hard dependents (what it unblocks), then key. It uses no new-skill slot and is placed before class (c). Vectors `pack-applied-gap-micro`, `pack-applied-gap-focus`. The practice fill (step 5) skips a second problem for a skill that already received one this way.
3. (c) New frontier skills in ranked order (6.3), while slots remain and backlog_suspend_new is false:
        same chunk as above (try 2 faded problems in focus, fall back to 1).
        Skip a `learning` skill whose loop_step is `done` (00a M1): its loop is complete and it waits for its
        FSRS review; it is not taught again as new. Vector `pack-loop-done-waits`.
4. (d) Interleaved practice: for each module (name order) with stage >= 1, not already used,
        >= 2 skills in {reviewing, mastered}: one interleaved set over the least-recently-strong skills,
        if it plus pending same-day retrievals fits.
5. Practice fill (focus only): round-robin one standard `problem` per learning/reviewing available skill,
        lowest retrievability first, max 2 per skill, keeping room for pending same-day retrievals.
6. (e) Due (not overdue) checkpoint: add if it fits.
7. Same-day retrievals: one `retrieval` per skill that received a faded_problem or new chunk, LAST in the
        session (spacing within the day, contract 7.3).
8. Return tasks ordered: overdue checkpoint, due reviews/verifications, continuation/new/applied-gap, practice and
        interleaved sets, due checkpoint, lab reviews, same-day retrievals. Assign positions 1..n.
```

**Loop-step transitions (made explicit by the design review; the reference simulation uses exactly these).** `skill_state.loop_step` moves only forward: new skill -> `worked_example`; after the chunk (worked example, faded problem(s)) -> `retrieval_same_day` until the same-day retrieval is submitted -> `practice`; `practice` -> `done` when one `problem` has been submitted (any score) **or** when `mastery_state` becomes `reviewing` or `mastered`, whichever is first; `verify` -> `done` when the skill reaches `reviewing`; a decayed skill whose relearning retrieval fails twice returns to `worked_example` (4.3). Only skills in `mastery_state = learning` with a loop step are *continuations* (step 2); this is why a skill that reaches `reviewing` before its practice step has run needs the applied-gap rule above.

Design notes:

- The same-day retrieval is always the last task. In a micro session with one new chunk and no other work it therefore follows the faded problem immediately, with 0 intervening tasks, which does not meet the "10 minutes or 3 intervening tasks" gap of 02 LS-006 / PRM-04 (found by the design review, 00f F-12). The scheduler only needs the card created after *some* retrieval; whether the gap matters for learning is unknown [inf].
- Sessions may **end short**. If nothing useful is eligible the fill is below 85%; the app says so ("That is everything useful for now") and never pads with low-value work. Early (not-yet-due) reviews are not added (`allow_early_filler` default false) because they add little [inf].
- A `lab` session with at least one eligible `project_step` (one that fits the budget) is `project_step`s in order, only steps that fit the remaining minutes, then up to `min(10, 10% of B)` minutes of due `retrieval` as `lab_review` at the end, not on `bench` context. **Lab fallback (00a G4):** when no project step is eligible (the step list is empty or no step fits), `pack_session` serves the slot as a `focus` session capped at `lab_fallback_cap_min = 120` minutes: it runs the whole focus procedure above with `available = min(available, 120)` and returns `served_as = "focus"`. The `plan_slots` row stays `lab` (status unchanged); the `sessions` row is created with `session_type = 'focus'`. Vectors `pack-lab-no-steps`, `pack-lab-step-too-big`, `pack-lab-short-no-steps`; `pack-lab` (steps present) is unchanged.
- Focus blocks: break prompt after 50 minutes of active time (user-adjustable, no physiological claim).
- When the learner finishes early or runs over, the builder is re-invoked with the remaining minutes (`rebuild` after each task if `actual - est > 25%` of the session).

Vectors: `pack-micro-phone`, `pack-micro-5`, `pack-focus-desktop`, `pack-interleave`, `pack-checkpoint-overdue`, `pack-bench`, `pack-lab`, `pack-lab-no-steps`, `pack-lab-step-too-big`, `pack-lab-short-no-steps`, `pack-micro-new-skill`, `pack-verify-inferred`, `pack-backlog-suspend`, `pack-focus-practice`, `pack-applied-gap-micro`, `pack-applied-gap-focus`.

Worked example (`pack-micro-phone`, 20 min phone): three due reviews (1.5 each, lowest R first), the in-progress `elec.dc.series-parallel` faded problem (5.0) and its same-day retrieval (1.5): 11.0 min, fill 0.55, no new skill because the single micro slot is used. (`pack-micro-new-skill`, same budget, no in-progress skill): 2 due reviews, worked example 4.0 + faded problem 5.0 + same-day retrieval 1.5 for `elec.dc.series-parallel`: 13.5 min.

### 7.5 Backlog rule

If overdue review minutes (count of due skills x 1.5) exceed `backlog_suspend_threshold_min = 120`, set `backlog_suspend_new = true` for micro and focus until it falls below 60, and raise the review share to 1.0. Shown as "Catching up on reviews first: N skills due."

### 7.6 Blocked-first, then within-module interleaving (concrete schedule)

A **skill group** = skills in the same module sharing `skills.confusable_set` (contract section 6; 02 LS-011: confusable sets are explicit content, 2 to 4 skills, never inferred at runtime). **A skill with no `confusable_set` is never interleaved** (it stays at stage 0). The earlier text said that without a tag the whole module is one group; that contradicted 02 LS-011 and the evidence, which supports mixing *confusable* problem types ("which method applies?"), not unrelated skills such as `sw.c.functions` and `sw.c.bitwise-ops` [V, Brunmair and Richter 2019 via 02 M03]. Graph 0.2.0 carries **11 `confusable_set` tags covering 30 skills** (00a G9; validator rule 14 requires every tag to have at least two members, all in one module): `dc-network-methods` (Kirchhoff, nodal, superposition, Thevenin/Norton), `opamp-configurations`, `rc-filter-type` (low-pass vs high-pass), `transistor-switches` (BJT vs MOSFET), `regulator-types` (linear vs switching), `calculus-operations`, `complex-forms` (rectangular, polar, Euler), `serial-protocols` (I2C vs UART), `value-vs-address` (pointer vs array), `probability-rules-vs-conditional` and `fsm-styles` (switch vs table-driven). Series vs parallel is one skill (`elec.dc.series-parallel`) and so cannot be a set. The reference `pack_session` takes the per-module stage from its caller and is unchanged. Interleaving applies only to templates with `body.interleavable = true` (default true for `problem`, `problem_short`, `perceptual_drill`, `debug_case`; false for definition/recall `retrieval`) [inf, `memory_practice_science.md` section 3: do not interleave vocabulary]. Cross-discipline interleaving is only in capstone `project_step` and `checkpoint` tasks.

| Stage | Switches on when | Behaviour |
|---|---|---|
| 0 blocked | always for a skill until it is `reviewing` | the skill is practised alone: worked example, faded problems, same-day retrieval, first reviews |
| 1 pairs | >= 2 skills in the group are `reviewing` or `mastered` | interleaved sets of width 2: 4 items alternating A B A B; each with a *strategy prompt* ("which method applies and why?") before the solve, the discriminative-contrast mechanism [R] |
| 2 triples | stage 1, >= 3 eligible skills, and the last 2 interleaved sets (since the last stage change) both scored >= 0.60 | width 3, 6 items round-robin |
| 3 module | stage 2, >= 4 eligible skills, last 3 sets all >= 0.70 | width = min(eligible, 5) |
| regress | last set scored < 0.40 | one stage down, never below stage 1 while >= 2 eligible; the weakest skill in the set gets a blocked `retrieval` + worked example next session |

Function `interleave_stage(eligible, sets, current)`; vectors `inter-single`, `inter-pairs`, `inter-to-triples`, `inter-regress`. Sets never put the same skill back-to-back (`round_robin_order`). Interleaved items are `problem_short` and count as ordinary reviews for each skill (one review per skill per session, 3.3). Experiment flag `interleaving` (section 11): control = stage 0 forever (blocked); treatment = this schedule.

### 7.7 Load balancing across nodes in a week

- Track `node_minutes` = minutes spent on new-skill and practice tasks per node over the trailing 7 days.
- A frontier skill's score is reduced by `2.0 x max(0, node_share - 0.60)` (6.3), so no node takes more than about 60% of the new-material time while another node has available skills.
- Reviews are not balanced (they are owed).
- The weekly plan reserves, per week, at least 1 new-skill chunk for each of up to 3 nodes with available frontier skills (`min_node_touch`), so `sw` is not starved while `elec` is deepened. Set per-node weights in settings later; MVP default equal.

### 7.8 Weekly plan generation (default 480 min/week)

Function `weekly_plan_slots(W)`:

```
lab_len   = W >= 300 ? clamp(round_to_30(0.375 * W), 120, 240) : 0
micro_len = W >= 360 ? 20 : (W >= 150 ? 15 : 10);   micro_n = 5
remaining = W - lab_len - micro_n * micro_len
focus_n   = remaining >= 90 ? 2 : (remaining >= 45 ? 1 : 0)
focus_len = clamp(floor(remaining / focus_n / 15) * 15, 45, 120)
slack     = W - planned
```

W = 480 -> 5 x 20 micro + 2 x 90 focus + 1 x 180 lab = **460**, slack 20 (vector `week-480`). W = 300 -> micro 15, focus 2 x 45, lab 120 = 285 (`week-300`); W = 240 -> no lab, 2 x 75 focus (`week-240`); W = 600 -> 5 x 20, 2 x 120, 1 x 240 = 580 (`week-600`).

**Slot placement defaults** (learner-editable in settings): micro Mon-Fri, context `phone`; focus Tue and Thu evening, `desktop`; lab Saturday, `desktop` (or `bench` when the step list says so). Rules: no two focus blocks on consecutive days; lab never the day before a focus block; at least 5 micro slots in 7 days so due reviews never wait more than 1-2 days (distributed practice [R]).

**Planning rate and the lab slot (00a G4, G8).** The plan is sized for **5 to 7 new skills a week**. On the builder's costs the 480-minute plan holds about 252 usable non-lab minutes; the Saturday lab slot adds 180 minutes only if a project step is eligible, otherwise it is served as a focus session of up to 120 minutes (7.4), which is what makes 5 to 7 new skills plus their reviews fit. Once a project step is eligible the lab slot is spent on the build and the learning minutes fall back to the non-lab ones, so the founder should expect new-skill throughput to dip when the first lab steps begin (section 14.3).

The weekly plan stores **slots only**, not contents; tasks are chosen just in time at session start because state changes. The plan screen shows a *forecast* ("about 14 reviews due, 2 new skills likely") computed from the current state, labelled as an estimate.

### 7.9 Rebalancing when sessions are missed (function `rebalance`)

A slot whose day has passed without a started session becomes `missed` at 04:00 local the next day. Never use guilt copy.

| Missed | Action |
|---|---|
| `micro` | Not made up as micro (reviews simply remain due and are picked up first next time). If **>= 2** micro slots are missed in the week and fewer than 7 micro exist, add **one** extra micro on the first remaining free day. |
| `focus` | Move to the first remaining day this week that has no focus within one day and no lab; otherwise carry `min(120, planned/2)` minutes to next week's focus (50% rule). |
| `lab` | Move to the last free day this week; otherwise carry in full to next week (cap 240). |
| any | Total planned minutes for the next 7 days is capped at **1.25 x** `weekly_minutes_target`; the lowest-priority extra slots are dropped first. |
| 2 weeks in a row at < 50% of target | Propose (never impose) a lower target = median completed minutes of those weeks rounded up to the next 30 and the same plan shape; UI copy neutral. |

Vectors: `rebal-focus-moved` (missed focus on day 1, moved to day 6 since day 4 is adjacent to the day-3 focus and day 5 holds the lab), `rebal-two-micro`, `rebal-lab-moved`.

## 8. Checkpoint scheduling (contract 7.7)

- **Module checkpoint:** due when >= 80% of the module's skills with `tier_target <= current target` are `reviewing` or `mastered` and no module checkpoint in the last 7 days.
- **Global checkpoint:** every 14 days. Status `due` from day 12 (reserve window), `overdue` at day 14 (function `checkpoint_status`). For a learner who has never taken one, the global clock starts on the day they first have >= 5 skills `reviewing`/`mastered`; the caller passes `days_since_last = 12` on that day (so it is `due` immediately).
- **Content:** fresh verified items, no hints, no tutor, no variant seen in the last 30 days, interleaved within the module (module scope) or sampled across nodes (global scope: up to 8 skills drawn from `reviewing`/`mastered` weighted by `(1 - R) + 0.1`, at least 2 nodes if available). Length cap 25 minutes (about 8-10 items at 2.5 min each). Item tier = the skill's current `tier_attained` or `tier_target`, whichever is higher.
- **Placement:** overdue -> first in the next session (any type but `lab`); due -> appended when it fits; module checkpoints are preferably a `focus` session.
- **Effect:** checkpoint attempts are normal attempts with `unaided = true`, count toward mastery and tier (L2 requires one), update Elo with weight 1.0 and feed FSRS (a failed checkpoint item on a mastered skill is rating 1 and decays it). Results also feed the evaluation (section 12). Never labelled "exam" in the UI.
- **Missed checkpoint:** stays overdue and keeps priority 0; it does not accumulate multiple instances.

Vectors: `cp-none`, `cp-due`, `cp-overdue`, `cp-module`.

## 9. Hints, tutor, and over-reliance

- Hint ladder levels are defined in the contract. The scheduler only consumes `max_hint_level`.
- **Reliance metric** per skill and global: share of the last 20 attempts with `max_hint_level >= 2`; flagged when >= 8 attempts and share > 0.5 (function `hint_reliance`). Vectors `hint-reliance`, `hint-reliance-high`.
- Responses: (1) per-skill flag -> the builder inserts one *hint-locked* `retrieval` (tutor button disabled until a first answer is submitted, as always, and hints capped at level 1) for that skill in the next session and shows a neutral note ("This one has needed help the last few times; try one on your own"); (2) global share > 0.6 over 30 attempts -> module checkpoint interval drops from 14 to 7 days for 3 weeks. Neither blocks the tutor.
- **Over-reliance trigger (00a G6, function `tutor_overreliance`; thresholds [P]).** Per node. For each of the last two checkpoints the caller supplies `unaided_n`/`unaided_correct` (strict-unaided checkpoint attempts of the node, 7.14 of the contract) and `aided_n`/`aided_correct` (attempts on the same skills since the previous checkpoint with `max_hint_level >= 1` or a tutor panel opened). Pooled over the two checkpoints, flag when `aided accuracy - unaided accuracy > 0.15` (`reliance_gap_threshold`) and both pools have at least 10 attempts (`reliance_min_attempts`). Effect: `tutor_mode = post_attempt_only` for the node, meaning the tutor answers only after the learner has submitted an attempt for the item at hand and gives no pre-attempt hints; it is re-evaluated at every checkpoint, so it lifts when the gap closes (vector `reliance-recovery`). Fewer than two checkpoints or fewer than 10 attempts on either side: no decision. Logged as `hint_reliance_flag` with `scope = node` and the gap. This replaces the weaker response of 00f F-15's first proposal (a 0.25 checkpoint-gap cap on hints) with the ratified G6; the per-skill and global hint-share responses above remain as earlier warnings. Vectors `reliance-trigger`, `-exactly-threshold`, `-just-over`, `-too-few-attempts`, `-one-checkpoint`, `-recovery`, `-unaided-better`, `-uses-last-two`.
- Hint attempts can never be qualifying, so reliance cannot buy mastery.

## 10. Edge cases

### 10.1 New learner

1. Offer the diagnostic (5.5) at first launch, skippable. Skipped: all `unseen`, `theta = 1300`, frontier = roots (`frontier-empty`: `math.alg.exponents-logs`, `math.alg.linear-equations`, `sw.c.variables` in the sample graph) ranked by project pull and unlocks.
2. First 3 sessions ("orientation"): no reviews exist, new-skill slots as normal, the first micro is 8-12 minutes with one skill chunk and a same-day retrieval, to establish the habit and calibrate time multipliers.
3. FSRS cards appear only after the first same-day retrieval.
4. `weekly_minutes_target` is asked in onboarding (default 480); the plan is generated immediately.

### 10.2 Long absence

Let `gap` = days since the last completed session.

- `gap < 14`: normal.
- `14 <= gap < 60`: **return session**: cap due reviews at 12 items in the first session (priority: prerequisites of in-progress/frontier skills first, then lowest R). The remaining reviews stay due and are taken in order across the next sessions; `backlog` flag applies. No re-scheduling of `due` (FSRS already reflects the delay in R). Weekly plan resets to the default shape for the current target.
- `gap >= 60`: additionally run a **re-entry check**: one `retrieval` for each of up to 8 skills sampled from `mastered`/`reviewing` (stratified by node, highest stability first). If average score >= 0.75 proceed as above; otherwise the nightly job has already set skills with R < 0.70 to `decayed`, and the app states the number plainly ("12 skills need a refresher"). The frontier shrinks automatically (6.1).
- Pause: a "pause until" setting suppresses notifications and missed-slot marking; it does not alter cards.

### 10.3 Failing a skill repeatedly -> drop to a prerequisite (explicit trace rule)

*Stuck detection* (`is_stuck`): a skill is **stuck** when its recent graded attempts show either (a) the last **3** attempts all have `score < 0.5` (or a hint-4 reveal), across **>= 2 distinct items and >= 2 local days**; or (b) **>= 2 of the last 4** attempts ended in a hint-4 reveal. Scaffolded `faded_problem` attempts count; `worked_example` does not exist as an attempt. A cooldown of 3 days applies after any trace.

*Trace* (`trace_back(skill, probe_results, depth)`, max depth 3):

1. `H` = direct **hard** prerequisites of the stuck skill s.
2. **Suspects** = those in `H` that are not satisfied under 6.1 (not mastered, and not reviewing with R >= 0.8). If suspects exist, they are the faulty set (`source = state`); go to 4.
3. Otherwise order `H` by theta ascending (key as tie-break), take at most 4, and issue **one unaided retrieval probe each** on a fresh variant (status `probe_needed`, the builder puts them first in the next session, reason `trace_probe`). When results arrive: a prerequisite with probe `score < 0.5` is faulty (`source = probe`). If none is faulty -> go to 5.
4. For each faulty prerequisite p: if p was `mastered`, set `mastery_state = decayed` (rating 1 logged with flag `trace_probe` if from a probe); otherwise leave its state and give it top priority in continuation or review (`prioritise`). Then set `s.blocked_by += p`, and recurse the same trace on p (depth + 1, stop at depth 3). s stays `learning` but is **removed from continuation/new selection** until every `blocked_by` skill is again `mastered` or `reviewing` with R >= 0.8, then `blocked_by` clears and s resumes at `worked_example`. The learner sees: "We are going back to <p> first, because it looks shaky: <evidence>".
5. No faulty prerequisite: the problem is **specific to s**. Restart s's loop at `worked_example` with a different template if one exists, reset `epoch_start`, and log `content_review_flag(skill, templates)`. If s is stuck again after this restart, flag its templates `needs_human_review` (visible only to the founder per contract 7.8) and offer the tutor with a "show where my thinking went wrong" prompt.

Vectors: `stuck-yes`, `stuck-same-day` (3 failures on one day are not yet stuck), `stuck-reveals`, `trace-state-suspect`, `trace-probe-needed`, `trace-probe-fail-recurse`, `trace-skill-specific`.

### 10.4 Gaming and degenerate behaviour

| Behaviour | Defence |
|---|---|
| Rapid random answers | `rapid_guess` flag (wrong, < 3 s and < 15% of expected): half Elo weight, no item update, still rating Again; 5 flags in 20 attempts shows a neutral "slow down" note, no penalty beyond the wrong answers |
| Memorising answers of repeated variants | fresh seeds, answer-string dedupe over last 5, difficulty-matched template rotation |
| MC guessing | guessing floor in E; MC never Easy; mastery needs a constructed-response qualifying attempt |
| Reveal-and-copy | hint 4 ends credit, score 0 for Elo, rating Again |
| Skipping hard items | a `skip` is not an attempt; the same due item skipped 3 times in 7 days becomes rating 1 on the skill; skips are logged |
| Confidence always 5 (or constant) | if variance of confidence over the last 30 attempts is 0, confidence-based rules (Easy, high-confidence error) are ignored for that learner |
| Tutor extraction | attempt-first policy (contract 7.9); hint attempts never qualify for mastery |
| Clock manipulation / editing device time | all timestamps server-assigned at sync; offline attempts keep a client time but days are computed from `submitted_at` clamped to server `received_at`; mastery days use server receipt date if the client time differs by more than 36 h; an offline attempt counts toward mastery, Elo and FSRS only after server verification (00a section C, contract 7.10) |
| Repeated same-day sessions to hit "2 days" | rule uses local calendar days, not session counts |

## 14. Workload simulation and parameter sensitivity (re-run for contract v1.2, 31 Oct 2026)

Purpose: answer "does an 8-hour week cover new learning plus reviews?" with numbers. Everything in this section is an **[inf] model output, not evidence**. The simulator is `python3 reference/scheduler_reference.py sim 12 8` (needs PyYAML; 12 weeks, seeds 0 to 7; about 3 minutes). It drives the real `pack_session`, `mastery_state`, `needs_applied`, `tier_attained`, `compute_frontier`, `desired_retention` and `weekly_plan_slots` of this reference with the real `content/mvp-skill-graph.yaml` (graph 0.2.0: 142 skills, 247 edges) and a synthetic learner, over the plan of `weekly_plan_slots(480)`: 5 micro of 20 minutes (Monday to Friday, phone), 2 focus of 90 (Tuesday and Thursday, desktop), 1 lab of 180 on Saturday. **Since contract v1.2 the Saturday slot has no project step in the simulation, so the packer serves it as a focus session capped at 120 minutes (G4)**; the earlier version of this section simulated it as dead time. Non-lab session time is 280 minutes a week, 252 after the 10% slack; with the fallback the usable time is about 360 minutes. Model assumptions, all [inf] unless stated:

- Memory: a simplified FSRS-5-like curve with default weights **recalled from memory [R]**, not the pinned FSRS-6 library; interval equals stability at the current `desired_retention` (0.85, then the switch rule of 3.5 driven by the simulated calibration monitor), cap 180 days. Reviews of a fresh variant succeed with probability R (the "pessimistic" scenario subtracts 0.10 and multiplies stability growth by 0.7). Ratings after success: Hard 12%, Good 83%, Easy 5%.
- Learner: success on a new skill's same-day retrieval 0.85; no skipped sessions unless stated; unaided, no hints, items always at the skill's tier; one template per skill unless stated (the lean slice has 30 to 40 templates for 142 skills, 00d).
- Time: `TASK_MINUTES` of 7.2; scenarios "x1.5" and "x2.0" make every task take that multiple of its estimate.
- Loop-step transitions as in 7.4; a global checkpoint every 14 days; interleaving stages from the count of `reviewing`/`mastered` skills per module with set accuracy 0.75. Mastery uses the v1.2 rule (span 2 days; template diversity only in the "2 templates" row). The latency gate and the tutor trigger do not enter the simulation.

Reading, with the effect of each ratified change. (i) **The applied-gap rule (G2) is the largest single lever**: 87 against 60 mastered at week 12; without it `reviewing` skills that lack only the applied attempt starve and the frontier collapses to 1.2 skills. (ii) **G3 costs about 6 mastered skills at week 12** (span 2 and one template: 87 against 93 under the v1.1 rules; a span of 4 days costs another 6) and **the template-diversity condition costs about 11 more when every skill has two verified templates** (76 against 87), because the second template is not always the one the Elo selection picks; this is the price of not letting one easy template supply every qualifying attempt, and it applies only to skills that actually have two verified templates, so in the lean slice (mostly one template per skill) it is rare at first. (iii) **G5 retention at 0.85 for the first 8 weeks lowers mastered skills at week 12 by about 4 in this model** (87 against 91) while reducing the review share by 5 points (39 against 44%) and the review minutes a week from 150 to 139 in weeks 7 to 12. The earlier claim of the design review that 0.85 raises mastered skills by 5 came from a model in which reviews were the bottleneck; with the applied-gap rule the bottleneck is the third qualifying attempt, which a shorter interval would help, and a longer interval delays; so 0.85 is chosen for the review load and the unvalidated fresh-variant risk (3.8), not for speed. At 1.5 times the builder costs the learner masters 5.7 skills a week (68 in 12 weeks) and at 2.0 times 4.2 a week, which is where the planning rate of **5 to 7 new skills a week** comes from. (vi) The lab slot served as a focus session (G4) is already included in every row; the simulator of contract v1.1 treated that slot as dead time, so its totals are not comparable.

### 14.5 Diagnostic length

The 5.5 algorithm of v1.2 on the real graph, 200 simulated learners per cell). Learners whose knowledge is the ancestor closure of a few random seed skills (novice: 3 skills of depth 1 to 3; some background: 6 of depth 3 to 6; strong: 6 of depth 6 to 11), slip 10% on known skills, 3% chance of a correct guess on unknown skills. "Placed known (not known)" counts skills wrongly credited, "placed unknown (known)" skills wrongly sent to teaching. Item caps: 10 (one sitting, 25 minutes), **20 (two sittings, the ratified design)**, 40 (the old unconstrained reference, 100 minutes).

| Profile | Item cap | Items used | Skills still unresolved (of 142) | Placed known (not known) | Placed unknown (known) |
|---|---|---|---|---|---|
| Novice | 10 / 20 / 40 | 10 / 20 / 30 | 50 / 16 / 0 | 2.0 / 2.8 / 2.9 | 0 / 0.3 / 0.6 |
| Some background | 10 / 20 / 40 | 10 / 20 / 39 | 57 / 28 / 2 | 1.4 / 1.4 / 2.0 | 0.4 / 0.9 / 1.5 |
| Strong | 10 / 20 / 40 | 10 / 20 / 40 | 67 / 40 / 11 | 0.7 / 1.2 / 1.6 | 1.4 / 1.9 / 2.4 |

At 2.5 minutes an item, 20 items is 50 minutes in two sittings of 25. Resolving nearly the whole graph would need about 30 items for a novice and 40 or more for a learner with background, which is more than the design allows; so a quarter of the graph (16 to 40 skills) stays unresolved and is treated as `unseen`, with the "I already know this" skip (5.6) covering the rest. With a 10% guess rate (an MC-like item) a novice is wrongly placed on 8 to 10 skills, which is why 5.5 forbids MC in the diagnostic. These are model outputs for an idealised down-set learner [inf]; real knowledge is not a perfect down-set.
