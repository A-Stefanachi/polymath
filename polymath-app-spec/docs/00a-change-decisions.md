# 00a — Ratified decisions on contract change requests

Status: **binding**. This file resolves every CONTRACT CHANGE REQUEST (CCR/CR) filed by documents 01–12. Where a document disagrees with a decision here, **this file wins** and the document must be edited to match. IDs (FR-, US-, LS-, PRM-, EXP-, T-PRJ-, ADR-, etc.) must NOT be renumbered during reconciliation.

## A. Sessions and time

| ID | Decision |
|---|---|
| A1 | Session types stay `micro` (5–20 min), `focus` (45–120 min), `lab` (120–240 min). There is **no session type for 21–44 minutes**. A window of 21–44 minutes is served as **one micro session, optionally chained to a second micro session** (the second counts as a separate `sessions` row). Project steps must not be authored in the 21–44 minute range. (Resolves arch CCR-7, UX-1, projects CR-2.) |
| A2 | A diagnostic is stored as a `focus` session whose tasks have `task_kind = 'diagnostic'`. `diagnostic` and `checkpoint` are **session-level task kinds**: they are not listed per skill in `skills.task_kinds`. (Resolves UX-2, 05 #5.) |
| A3 | Project `L5` (first KiCad board) is **fully specified in this package but is the last item built (milestone M5)**. The MVP ladder for early milestones is L0–L4. (Resolves projects CR-1.) |

## K. Teaching layer (4 Nov 2026)

The founder reported that the app "is not really teaching" and asked for research on how to teach the curriculum. The agent found two gaps: the worked example showed only the problem statement (H1 was never built and the OpenAPI file had no field for steps), and the loop had no step that explains an idea before practice. The founder accepted the agent's recommendation on 4 November 2026 ("create the specs for it"). Evidence is in doc 02 M14; every effect size there is [S] or [R].

| ID | Decision |
|---|---|
| K1 | **Teaching model.** A new skill is taught as: concept primer (K6 to K9), then the worked example as a stepper (K2, K4), then faded problems (K3), then the same-day retrieval and the rest of the loop of doc 06, unchanged. The primer and the stepper are one `worked_example` task. There is no new `task_kind`, no change to the scheduler, the mastery rule, FSRS or the reference vectors. |
| K2 | **Worked steps reach the learner only through `getTask`.** `LearnerItem.rendered` gains `worked_steps` (array of `{id, label?, text_md}`), `steps_total` (integer) and, for worked examples only, `explanation_md`. The serve path fills them from `item_secrets.solution` only when the item is reached through `getTask` for a session task that belongs to the caller and whose `task_kind` is `worked_example` or `faded_problem`, and the item's template is in the `practice` pool. `getItem`, every other task kind, assessment and transfer items, checkpoints, diagnostics and offline packs never carry them (offline packs are decided with D6). A `worked_example` carries every step. Showing the steps cannot inflate a grade: a worked example is never graded (LS-008), a faded problem never shows its final step, and an item's seed is never served to the same learner again (LS-002). This is an explicit, narrow exception to "learners never read `item_secrets`" (CLAUDE.md rule 6); the solution stays in `item_secrets`, which keeps no client grant. |
| K3 | **Fading positions (refines H1 and LS-007).** For a template with 2 or 3 steps, every `faded_problem` hides the last step (H1). For a template with 4 or more steps, the first `faded_problem` of the skill in a session hides every step after `floor(n/2)`, and the second hides every step after the first. The learner always answers the item's normal answer prompt, so graders are unchanged. |
| K4 | **Self-explanation is "pick the step's purpose".** In the stepper, when the template's steps carry labels (K5), each revealed step asks "What is this step doing?" with the labels of that item's steps as the choices (shuffled, no penalty, the answer is shown at once). Without labels, the stepper shows one optional free-text prompt at the end. The choices and the text are stored in `CompleteTaskRequest.self_explanation` as before and never graded (LS-008). Typed self-explanation is optional, not mandatory: the 2023 math meta-analysis of worked examples found added self-explanation prompts lowered the benefit [S]. Doc 09 S08 already allowed "or choose the reason". |
| K5 | **Optional step labels.** `solution.steps[]` in `schemas/problem-template.schema.json` gains an optional `label` (1 to 60 characters): the step's goal written as a short imperative, for example "Convert the current to amperes". Lint: a template with 4 or more steps must label every step. Adding a label changes the template hash and voids its review (doc 07 T9). Now in scope: label and, where the method needs it, expand to 4 to 6 steps the multi-step electronics templates `tpl.elec.kirchhoff-kcl`, `tpl.elec.nodal-unknown`, `tpl.elec.thevenin-model`, `tpl.elec.voltage-divider-vout` and `tpl.elec.parallel-pair`. Other templates gain labels only when they are next edited for another reason. |
| K6 | **Lessons are a content type.** One file per skill, `content/lessons/<skill_key>.yaml`, validated by `schemas/lesson.schema.json` and `reference/validate_lessons.py`. A lesson has at most 3 screens of at most 150 words each, an optional SVG figure per screen, exactly one misconception block (wrong idea, why it is tempting, the correct idea, and a `tag` that matches a misconception tag of one of the skill's templates when one exists), 1 or 2 deterministic multiple-choice checks with feedback per option, and a recap of at most 60 words. Files declare `authoring_status` `draft`, `ready` or `retired`, like templates (D4). A skill with no verified lesson starts at the worked example as today. Lessons are drafted with an LLM and reviewed by the founder (rule 4: the LLM drafts, it never decides); `pnpm claims:lint` covers them. |
| K7 | **Table `skill_lessons`.** Columns: `id`, `skill_key` (references `skills.key`), `version`, `status` (`content_status`), `body` (jsonb, the validated file), `content_hash`, `license`, `source`, `reviewed_by`, `reviewed_at`, `retired_at`, timestamps. Unique `(skill_key, version)`; one row per version. RLS: learners select rows with `status = 'verified'`; admins select and write all. Grants: select to `authenticated`, insert, update and delete to `authenticated` (filtered by the admin policy), all to `service_role`. The body holds no secret: the correct option of a primer check is visible to the learner by design, because checks are never graded and never reach `skill_state`. |
| K8 | **Lesson delivery.** `TaskDetail` gains an optional `lesson` (`LessonView`) on a `worked_example` task when the skill has a verified lesson. `variant` is `full` when the caller has no graded attempt on the skill yet, else `recap` (relearning after decay, or a loop restart of doc 06 section 10.3). Skills that start from the diagnostic or "I already know this" never get a worked example, so they never see a primer. The learner can skip to the example at any time. Primer checks are answered in the client; they create no `attempts` row and no grade. When a graded attempt carries a `misconception_tags` entry equal to the lesson's `misconception.tag`, the feedback panel offers the lesson's correct idea and a link to the recap. |
| K9 | **Lesson review and versions.** `content:sync` writes a `ready` file as a new `skill_lessons` version with `status = 'needs_human_review'` whenever its hash changes; it never sets `verified`. The founder approves the version in the review console (`/admin/content`, as in J5), which sets `verified`, `reviewed_by` and `reviewed_at` for that hash only. Learners get the newest verified version; an older verified version stays verified until a newer one is approved. A `retired` file retires every version. |
| K10 | **Two events.** `lesson_viewed` (`skill_key`, `lesson_version`, `variant`, `screens_seen`, `skipped`, `dwell_ms`) when the primer closes, and `lesson_check_answered` (`skill_key`, `lesson_version`, `check_id`, `correct`) per check. Both join the catalogue of doc 11 section 9. They are analytics only and never drive scheduling. |
| K11 | **Time budget unchanged.** The `worked_example` estimate stays 4.0 minutes (doc 06 section 7.2) and now covers the primer and the stepper, so the reference vectors are untouched. The orientation sessions' actual-to-estimate ratio (06 section 7.2) corrects it if it is wrong. |
| K12 | **Scope and order.** New lean tasks BL-0198 to BL-0205 (Wave 6b of the factory manifest) land before the M1 exit test BL-0069, so the two-week dogfood and the go/no-go (BL-0181) judge an app that teaches. BL-0069 gains BL-0199 and BL-0202 as dependencies. Not adopted: a new `lesson` task kind, lessons generated by the tutor at run time, videos or links to outside courses as the lesson, productive failure for beginners (LS-092 stands). |
