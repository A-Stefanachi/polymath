Content pipeline and verification

docs/07-content-pipeline-and-verification-spec.md, Content authoring runbook, Population roadmap, lean-skill-slice.yaml, REVIEW-LOG.md, sample-problem-templates/, content/templates/ (lean pool), lean-template-manifest.yaml, content/safety/

Summary

  • Skills, templates, and projects are version-controlled YAML, not CMS entries.
  • Continuous integration validates schema, licensing, and graph consistency.
  • Verification regenerates items and independently recomputes expected answers.
  • content:sync upserts verified content into PostgreSQL; runtime serves only verified items.

Pipeline stages

  1. Authors edit files under content/.
  2. Validators check graph, template schema, and claims policy.
  3. Generation produces item instances and verification_report artifacts.
  4. Human review resolves needs_human_review statuses where required.
  5. Deployment workflow synchronizes approved content to the target database.
  6. Application layer selects items by identifier; unverified statuses are excluded.

Template identifiers

Format: tpl.{node}.{slug} (example: tpl.elec.voltage-divider-vout). Each template declares task kind, grader type, parametric body, licence, and source metadata.

Prompt assets

Tutor, rubric, and drafting prompts reside in content/prompts/ and are referenced by identifier from LlmClient implementations.

Model-assisted drafts require verification because error rates prior to independent checks are material; the serve gate exists to enforce quality, not to bypass it.
